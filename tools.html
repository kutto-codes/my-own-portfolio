SECURITY TOOLS

A visual guide to tools I use in authorized labs.

I use these tools in practice environments to explore questions such as what services are available and how a web application handles traffic. The screenshots are examples from lab work. I only test systems I own or have permission to assess.

00

How I use these tools

I use each tool to explore a specific question in an authorized practice lab. The screenshots show examples of the interfaces and output I have encountered; results vary by setup, and a result by itself does not prove a vulnerability.

  • I confirm permission and the exact systems and activities in scope before testing.
  • I use a training lab or a system I own and keep checks limited to the agreed purpose.
  • I review what a tool reports, verify observations safely, and record only necessary evidence.
  • I protect captured traffic and other data, then share findings with the system owner.
01

Network discovery

HOST AND SERVICE MAPPING

Nmap

I use Nmap in authorized labs to identify reachable hosts and the network services they appear to expose. This helps me build an inventory and decide what to review.

The screenshots show terminal output summarizing ports and service information. I treat scan results as a starting point and interpret them in context rather than assuming they indicate a weakness.

How I use it in a lab: I choose an in-scope practice host, select a scan appropriate to the exercise, and review the reported hosts, ports, and services. I check unexpected results against the lab documentation.

WEB CONTENT DISCOVERY

Gobuster

I use Gobuster in authorized labs to check a web server for common paths and review the responses. This can help me find pages or directories that may need further review.

I interpret responses such as redirects and access-denied results carefully; a discovered path is not automatically a vulnerability.

How I use it in a lab: I point it only at the approved practice web app, select a wordlist suitable for the exercise, and review the returned paths and response codes. I check relevant results in the lab app and report only verified, in-scope observations.

02

Web application testing

HTTP INSPECTION

Burp Suite

I use Burp Suite as a web testing proxy to inspect requests and responses between a browser and an application, map the pages I visit, and investigate application behavior.

I use these views to organize an assessment and understand the application. I stay within the agreed scope and verify findings without accessing data I do not need.

How I use it in a lab: I configure a browser to use Burp's local proxy, visit the practice app, and review requests and responses in the history and site map. I begin with observation and change or replay requests only when the exercise permits it.

PACKET ANALYSIS

Wireshark

I use Wireshark to inspect network packets and examine communication between systems. Display filters help me narrow a capture to traffic relevant to a troubleshooting or defensive investigation question.

Because packet captures can contain sensitive information, I capture only where authorized, minimize collection, and protect or remove data when I no longer need it.

How I use it in a lab: I open a provided practice capture or select an authorized interface, then use display filters to focus on the relevant protocol or conversation. I inspect packet layers and avoid sharing captures that contain private data.

03

Framework overview

TESTING FRAMEWORK

Metasploit Framework

I use Metasploit in controlled environments to learn how security tests are organized and validated. Its modules support different assessment tasks, and its console provides an interface for managing them.

The screenshots show the framework starting up; they do not show a system being tested or compromised. I keep its use to a lab or an explicitly authorized assessment.

How I use it in a lab: I work only with an intentionally vulnerable training target. I read the module documentation, check it against the exercise, and follow the lab instructions; I do not run modules against public or third-party systems.

RESPONSIBLE PRACTICE

Scope first, evidence second

Before I use a security tool, I confirm written permission, the systems and activities in scope, and the rules for handling data. I choose the least intrusive checks that answer my question, record relevant evidence, and report results to the system owner.
